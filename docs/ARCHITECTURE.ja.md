# アーキテクチャ

## 全体像

このリポジトリは「コア（純粋ロジック）」「アダプタ（I/O）」「ユースケース」「適合性検証」
「インフラ（CDK）」を分離している。目的は 3 つ。

1. **AWS 資格情報なしで全部検証できる** こと（CI の信頼性）
2. **法令の要件をコードで追える** こと（監査の説明可能性）
3. **同じコードがローカルでも Lambda でも動く** こと（二重実装を避ける）

```text
                     ┌─────────────────────────────────────────────┐
                     │ src/app/  ユースケース                       │
                     │ createArchive: ingest / search / export /   │
                     │ verifyChain / audit / reindex               │
                     └───────┬─────────────────────────┬───────────┘
                             │                         │
        ┌────────────────────▼──────────┐   ┌──────────▼─────────────┐
        │ src/core/  純粋ドメイン         │   │ src/compliance/         │
        │  canonical / hash / chain     │   │ 20 ルール + 監査エンジン  │
        │  index-keys / query / export  │   │ レポート（Markdown/JSON）│
        │  time / timestamp             │   └──────────┬─────────────┘
        └───────────────────────────────┘              │
                                                       │ InfraSnapshot
        ┌───────────────────────────────┐   ┌──────────▼─────────────┐
        │ src/adapters/                 │   │ src/cdk/  4 スタック    │
        │  local/ … ファイル・JSON       │   │  synthAll() でオフライン  │
        │  aws/   … S3 / DynamoDB       │   │  合成（資格情報不要）    │
        └───────────────────────────────┘   └────────────────────────┘
                    ▲
                    │ src/cli/ と src/handlers/ が app を呼ぶだけ
```

依存の向きは常に `core → app → adapters/cli/handlers`。コアは外側を知らない。

## データモデル

```text
VoucherInput（取り込み入力）
  └─ content: Uint8Array ──────────────┐
                                       ▼
                              SHA-256（内容アドレス）
                                       │
  VoucherMetadata ── hash ──► StoredMetadata（タイムスタンプを含む封筒）
                                       │
                                       ▼
                              LedgerEntry（ハッシュチェーンの1項）
```

### 不変条件

| 不変条件 | 破られたときに起きること | 検出方法 |
| --- | --- | --- |
| 本体のハッシュ = 保存キー | 本体の差し替え | `content-mismatch` |
| メタデータ封筒のハッシュ = 台帳の値 | メタデータの差し替え | `metadata-mismatch` |
| `previousEntryHash` = 直前の `entryHash` | 削除・並べ替え | `chain-link-mismatch` |
| エントリ内容の再計算 = 保存された `entryHash` | エントリ自体の書き換え | `entry-hash-mismatch` |
| タイムスタンプのダイジェスト = 本体+メタデータ | 時刻証明の差し替え・再利用 | `timestamp-mismatch` |

## ハッシュチェーン

```text
entryHash = SHA-256( canonicalJson({
  sequence, previousEntryHash,
  voucherId, objectKey,
  contentSha256, metadataSha256, timestampSha256,
  recordedAt
}) )
```

### なぜ「封筒」にタイムスタンプを入れるのか

タイムスタンプはメタデータのハッシュに依存し、そのハッシュがタイムスタンプに依存する…
という循環を避ける必要がある。本実装は次の順序で解決している。

1. `metadataDigest = SHA-256(canonical(VoucherMetadata))`（タイムスタンプを含まない）
2. `attestationDigest = SHA-256("dencho-attestation/v1:" + contentSha + ":" + metadataDigest)`
3. TSA が `attestationDigest` に対するトークンを発行
4. `StoredMetadata = { metadata, timestamp }` をハッシュして `metadataSha256` とする
5. 台帳は `metadataSha256` と `timestampSha256` の両方を記録

これにより、本体だけ・メタデータだけ・トークンだけを差し替えても検出できる。

### 検証の順序と打ち切り

`verifyLedger` は **先頭から順に** 次の 5 段を検査し、最初に壊れた位置で停止する。

1. 連鎖（`previousEntryHash`）
2. エントリハッシュ（再計算）
3. 本体オブジェクト（存在 + ハッシュ）
4. メタデータ封筒（存在 + ハッシュ + `timestampSha256`）
5. タイムスタンプの署名検証（TSA を渡した場合）

停止するのは、壊れた地点より後ろの情報が信頼できないからである。
戻り値は `ChainBreak`（位置・理由・期待値・実際値・証憑ID）で、
`checkedEntries` には「完全に検証できた件数」が入る。

チェックポイントは「ある時点の head を固定した記録」で、
台帳の途中までの書き換えを検出する補助になる。チェックポイント自体が
食い違った場合は `status` は `intact` のまま `checkpointsVerified: false` を返し、
AUTH-04 がそれを不適合として扱う（チェーン全体を読み直さずに検出できる）。

## 取り込みの原子性

```text
1. 入力検証（法定 3 項目が揃っているか、金額は整数か、受領時刻は妥当か）
2. 冪等性チェック（同じ voucherId が既にあるか）
3. 本体とメタデータ封筒を内容アドレスで保存
4. 台帳へ追記（楽観的排他制御。競合したら読み直して再試行）
5. 検索索引へ登録（失敗したら台帳から再構築して回復）
```

4 と 5 を不可分にしないのは、**索引は台帳から再生成できる派生データ** だからである。
索引が壊れても `dencho reindex` で直せるが、台帳が壊れると証明が失われる。
そのため台帳への追記だけを原子的に行う。

DynamoDB 実装では `TransactWriteItems` で次を 1 トランザクションにしている。

- `ConditionCheck`: 先頭（HEAD）の `sequence` と `entryHash` が期待どおりか
- `Put`: 台帳エントリ
- `Put`: 新しい HEAD

先頭が変わっていれば `TransactionCanceledException` になり、
`ChainConflictError` として呼び出し側が再試行する。

## 検索索引の設計

### なぜ DynamoDB なのか

証憑の検索は「日付の範囲」「金額の範囲」「取引先」の組み合わせで、
これは DynamoDB のパーティションキー+ソートキーで表現できる。
S3 に索引を置くと全件走査になり、7 年分の証憑では成立しない。

### 索引表

`amountPadded` は金額を 16 桁ゼロ埋めした文字列で、**文字列順 = 数値順** になる。
`YYYY-MM` は取引年月日から作る月パーティション。

| 索引 | パーティションキー | ソートキー |
| --- | --- | --- |
| `by-date` | `D#YYYY-MM` | `<date>#<amountPadded>#<voucherId>` |
| `by-amount` | `A#<金額の10進桁数5桁>` | `<amountPadded>#<voucherId>` |
| `by-counterparty` | `C#<正規化取引先名>` | `<date>#<voucherId>` |
| `by-counterparty-date` | `C#<正規化名>#D#YYYY-MM` | `<date>#<voucherId>` |
| `by-counterparty-amount` | `C#<正規化名>#A#<桁数>` | `<amountPadded>#<voucherId>` |

金額のバケットに「桁数」を使うのは、範囲検索のアクセス回数を
**最大 16 回** に抑えられるからである（`0..9` = 1 桁 … 16 桁）。
固定幅の数値バケット（例: 10 万円刻み）だと、上限のない範囲検索で
バケット数が発散する。

### クエリプランナ

条件の組み合わせに対して「最小のアクセス回数で済む索引」を選ぶ。

| 条件 | 使用索引 | アクセス回数 |
| --- | --- | --- |
| 取引先 + 日付（両端あり） | `by-counterparty-date` | 月数 |
| 取引先 + 日付（片側） | `by-counterparty` | 1 |
| 取引先 + 金額 | `by-counterparty-amount` | バケット数（≤16） |
| 取引先のみ | `by-counterparty` | 1 |
| 日付のみ（両端あり） | `by-date` | 月数 |
| 日付のみ（片側） | `by-date` | 120 か月（10 年） |
| 日付 + 金額 | `by-date` + 金額は残条件 | 月数 |
| 金額のみ | `by-amount` | ≤16 |
| 書類種別のみ | 索引なし（残条件のみ） | 不可（併用を要求） |
| 条件なし | — | 不可（全件走査の禁止） |

`planQuery` は `rationale`（日本語）を返す。「なぜこの索引を選んだか」を
レポートと CLI に出せるので、検索要件の説明にそのまま使える。

### 検索要件の「証明」

`describeSearchCapability()` は固定値を返すのではなく、
**プランナを実際に走らせて** 3 項目・範囲・2 項目組み合わせの可否を導出する。
監査ルール `VIS-01..03` はこの結果を検査する。
「検索できると書いてある」ではなく「プランナが実際にその条件を扱える」ことを
検証する設計にしている。

## 適合性検証エンジン

```text
ArchiveView（台帳・証憑・チェーン検証結果・検索能力）
        +
InfraSnapshot（CDK が合成した CloudFormation）
        ↓
RuleContext → BUILTIN_RULES（20 ルール）→ RuleResult[] → AuditReport
        ↓
Markdown / JSON レポート、終了コード
```

- ルールは純粋関数。1 つが例外を投げても監査全体は止めず、`status: 'error'` として記録する
- 必須ルールに `fail` が 1 つでもあれば `non-compliant`（終了コード 1）
- 必須ルールに `error` があれば `incomplete`（終了コード 2）
- インフラ定義が無い場合、`INF-*` は `not-applicable`

特に重要なのが `AUTH-05` の扱いである。電帳法の真実性は
「タイムスタンプ」「訂正削除履歴」「WORM」「事務処理規程」のいずれかで確保する。
そのため:

- タイムスタンプ方式を採る（`requireTimestamp: true`）→ `AUTH-05` は対象外
- 採らない → `AUTH-05` が必須になり、WORM か履歴が無ければ不適合

「どれも採っていない」状態を必ず不適合にできるのが、この多方式モデルの要点である。

## 決定性

| 箇所 | 対策 |
| --- | --- |
| 正規化 | キーをソートし、整数のみ許可（`1.0` と `1` の揺れを排除） |
| ハッシュ | すべて正規化後のバイト列に対して計算 |
| 検索順序 | 既定は取引年月日の降順、同値は sequence 降順 |
| レポート | ルール順序を固定。Markdown の表をエスケープ |
| CSV | BOM + CRLF + RFC 4180 で固定。ファイル名は UTC コンパクト表記 |
| デモ | 固定クロックで実行 |

## 障害復旧

| 障害 | 影響 | 復旧 |
| --- | --- | --- |
| 索引の破損・欠落 | 検索できない | `dencho reindex`（台帳から再構築） |
| 台帳エントリの破損 | 証明が失われる | PITR（DynamoDB）で復元。ハッシュチェーンで改ざんを検出 |
| 本体データの改ざん検知 | 該当証憑が怪しい | Object Lock（WORM）で上書き自体を拒否。検出時は該当項を起点に調査 |
| 同時取り込みの競合 | 追記が失敗 | 楽観的排他制御で検出し、読み直して再試行（最大 5 回） |

## テスト戦略

| 層 | テスト | 何を保証するか |
| --- | --- | --- |
| コア | 単体 | 正規化・ハッシュ・チェーン・索引キー・クエリ計画の仕様 |
| アダプタ（ローカル） | 単体 | 原子書き込み・OCC・パストラバーサル拒否 |
| アダプタ（AWS） | 単体（偽クライアント） | リクエスト構築・エラー変換・トランザクションの使い方 |
| 適合性 | 単体 | 20 ルールの pass/fail と判定ロジック |
| CDK | アサーション | セキュリティ設定（Object Lock・BPA・PITR・IAM） |
| 統合 | E2E（ローカル） | 取り込み → 検索 → 出力 → 改ざん検知 → 監査 |
| CLI | E2E | 終了コードと出力形式 |

AWS 資格情報が無いため、実サービスに対する統合テストは行っていない。
代わりに「合成した CloudFormation を適合性エンジンに読ませる」ことで、
**インフラ定義と監査ルールが同じ世界を指しているか** を CI で検証している。

## 実装中に踏んだ不具合

記録として残す。同じ設計を選ぶ人が同じ穴に落ちないように。

| 症状 | 原因 | 対策 |
| --- | --- | --- |
| タイムスタンプが「受領時刻より前」になり AUTH-02 が誤検知 | `receivedAt` はミリ秒付き、記録時刻とタイムスタンプは秒精度。切り捨てで負の差分が出た | 受領時刻を秒精度に正規化し、付与時刻は `max(now, receivedAt)` を採用 |
| 証憑データの削除・並べ替えを検出できない | ハッシュを再計算すれば連鎖が繋がってしまう | `sequence` の連続性も検査し、`chain-link-mismatch` として扱う |
| 空のアーカイブでチェックポイント検証が失敗扱い | 空配列の扱いが未定義 | 空なら `checkpointsVerified: true` と定義 |
| `init` 直後に `manifest.json` が無い | 初期マニフェストをメモリ上にだけ持っていた | 初期化時にファイルを書き出す |
| CSV のファイル名に `+09:00` が残る | 生成時刻をそのまま埋めていた | UTC のコンパクト表記（`20261031T093000Z`）に変更 |
| 監査が「適合」なのに終了コードが 1 | AUTH-05 が推奨のまま常に fail していた | 多方式モデルに合わせて必須+条件付き対象外へ再定義 |
